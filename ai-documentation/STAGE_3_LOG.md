## 4. Technical Explanations

### Canvas Rendering
The canvas uses `window.devicePixelRatio` to scale the internal pixel buffer for Retina-grade sharpness. The underlying event coordinates are never modified; all transformations are executed via 2D Canvas context matrix operations (`ctx.translate`, `ctx.scale`). Line widths taper smoothly using $w(d) = (5.4 - d_{\text{norm}}^{0.65} \cdot 4.25) / \text{scale}$, ensuring prominent trunks and fine filaments.

### Progressive Growth
Growth occurs over a 2800ms timeline driven by `requestAnimationFrame`. Each recursion level $d$ is mapped to a normalized growth window $[d / (D + 1), (d + 1.25) / (D + 1)]$. Growth within each window uses cubic ease-out interpolation:
$$g(t) = 1 - (1 - t)^3$$
This ensures that parent branches finish drawing before child branches begin.

### Dynamic Camera Behavior
The camera calculates two framing states based on tree bounding boxes:
1. **$S_{\text{start}}$ (t = 0.0):** Zoomed in $1.7\times$ closer, anchored on the root trunk base.
2. **$S_{\text{full}}$ (t = 1.0):** Framed comfortably to encompass the full canopy with 24% horizontal and 20% vertical margins.

As the tree grows, camera scale and offsets smoothly interpolate:
$$\text{scale}(t) = S_{\text{start}} + (S_{\text{full}} - S_{\text{start}}) \cdot (1 - (1 - t)^3)$$
Manual panning and zooming are overlaid on top of this matrix cleanly.

## 7. Bugfix: Downward Tree Drift & Settling Resolution

### Debugging Prompt

### Root Cause Analysis
1. **Container Height Feedback Loop via ResizeObserver:**  
   In `handleResize()`, the renderer was measuring `this.container.getBoundingClientRect()` and setting `this.canvas.style.height = `${height}px``. Because the container has borders, setting the child element's inline height to the outer box forced the flex container to expand downwards on every measurement. This triggered `ResizeObserver` repeatedly, perpetually increasing `height`.
2. **Downward Y-Offset Growth Drift:**  
   Because `height` was constantly expanding in the loop, the vertical camera translation `autoOffsetYFull = height * 0.88 - rootY * autoScaleFull` grew larger on every single frame, continually translating the tree downwards indefinitely. In addition, `autoOffsetYStart` had a mismatched anchor multiplier ($0.78$ vs $0.88$), causing the root itself to slide downward during growth.
3. **Unterminated requestAnimationFrame Loop:**  
   When `progress >= 1.0`, the loop continued requesting frames via `requestAnimationFrame(this.renderLoop)`, which kept the re-measurement and re-rendering cycle running indefinitely even when growth had ended.

### Key Changes Implemented
1. **Eliminated Container Sizing Feedback Loop:**  
   - In `VisualizationPanel.tsx`, the canvas container is given stable, responsive CSS heights (`h-[480px] sm:h-[540px] lg:h-[620px]`).
   - The `<canvas>` element is positioned with `absolute inset-0 w-full h-full block touch-none`, isolating it from document flow.
   - In `handleResize()`, removed inline `canvas.style.width` and `canvas.style.height` assignments. Only internal bitmap dimensions (`canvas.width` and `canvas.height`) are adjusted for DPR, eliminating layout feedback.
2. **Fixed Constant Grounded Root Anchor Ratio (0.85):**  
   - Both start and full camera offsets anchor the root at the exact same anchor ratio:
     `autoOffsetYStart = height * 0.85 - rootY * autoScaleStart`
     `autoOffsetYFull = height * 0.85 - rootY * autoScaleFull`
   - This keeps the root grounded at exactly $85\%$ canvas height with zero vertical sliding or drifting during and after growth.
3. **Camera Settling & Loop Termination:**  
   - When `rawProgress >= 1.0`, `camEase` is clamped strictly to `1.0`.
   - The final settled frame is drawn once with `drawFrame(1.0, timestamp)`.
   - The animation frame loop is explicitly cancelled and stopped (`cancelAnimationFrame(this.animationFrameId)` and `this.animationFrameId = null`).
   - Re-rendering occurs only on user interaction (panning, zooming, resizing) or when "Replay Growth" is clicked.
